Scrip

A payment rail that makes bridged XRP spendable by software. Agents pay per call in FXRP, priced in USD by Flare's FTSO, holding no gas token.

How a payment works

An agent requests a paid endpoint. The server answers 402 with a price in US dollars. The agent signs one offchain EIP-2612 permit. The facilitator submits it, moves FXRP to the payee, and the endpoint returns its result. The agent never sends a transaction and never needs C2FLR. 

agent  --GET-->      endpoint     402 + price in USD
agent  --sign-->     permit       offchain, no gas, no transaction
relay  --settle()--> Flare        permit + transferFrom, relayer pays gas
agent  <--200--      endpoint     resource delivered

settle() binds each payment to an invoice ID, because a permit signature stays valid until its deadline. Without that binding a relayer could settle the same invoice twice.

It also measures what actually arrived. FAssets parameters are asset-manager controlled and may levy a transfer fee, so the contract reads the payee balance before and after and reverts with Underdelivered if the payee received less than the invoice. A payment rail that silently underpays is a broken one.

Why this needs Flare specifically

The point of the project is that it does not port to another chain by find-and-replace.

  • FAssets / FXRP is the settlement asset. FAssets gives XRP a way onto Flare; almost nothing gives it a reason to move. This is a demand-side use for the bridged asset.
  • FTSO prices every invoice. Invoices are denominated in USD and settled in FXRP at Flare's enshrined onchain feed, so the oracle is load-bearing rather than decorative.
  • EIP-2612, not EIP-3009. FXRP implements permit, not transferWithAuthorization. Every x402 implementation written for USDC assumes the latter, so the signing path here had to be built against Flare's actual token rather than adapted from a tutorial.

FXRP is resolved at runtime through the Flare Contract Registry rather than hardcoded, so a redeployment does not break the code. The testnet token reports its symbol as FTestXRP and its name as FXRP - use what the contract returns rather than assuming either.

Run the probe

Read-only. Needs no keys and spends no gas. It reports every fact the facilitator depends on, and fails loudly if signatures would not verify. 

git clone https://github.com/Ritapossible/Scrip.git
cd Scrip
npm install
npm run probe

It reads rather than infers, because FXRP ships a vendored ERC20Permit rather than stock OpenZeppelin - anything taken from upstream documentation is a guess. Two findings worth repeating: the EIP-712 domain rebuilt from eip712Domain() matches the token's own DOMAIN_SEPARATOR exactly, so signatures verify; and decimals is 6, not the 18 a standard ERC-20 would use.

Known limitation

EIP-2612 nonces are sequential per payer, so an agent paying two endpoints concurrently will have the second permit fail on a consumed nonce. EIP-3009's random nonces avoid this, but FXRP does not implement EIP-3009. Payments are serialised per payer until that is addressed.
